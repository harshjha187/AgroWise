## How to keep this file useful

- When a file's *purpose* changes (not just its contents), update its row above in the same session.
- When switching sustained focus to a different file, update **§ Currently active file** — replace the current entry, push the old one onto the breadcrumb trail.
- Don't turn the breadcrumb trail into an exhaustive changelog — that's git history's job once this repo has a remote. Keep it to enough entries to reconstruct "how did we get here," a dozen or so hops back at most.
- When a doc cross-references another doc's section number, and that doc gets restructured/renumbered, grep for the old reference across all `.md` files before moving on (this bit both `rules.md` and this file once already after `design.md` gained a new §3).
- **Be honest about what was actually verified vs. what hit an environment wall.** This session's Docker build and Xcode/Gradle builds were validated up to real, specific, named external-network/toolchain limits (container network egress blocked; `github.com` unreachable; no local Java) — not silently assumed to "just work." Carry that same discipline forward: state exactly what ran and what it hit, not a vaguer "should work."
